# Database

PostgreSQL 17. The schema is `apps/api/prisma/schema.prisma`; the migrations in
`apps/api/prisma/migrations/` are the source of truth for everything Prisma cannot express
([ADR-0002](decisions/0002-prisma-with-raw-sql-invariants.md)). This document catalogues the
entities, every invariant group with its rationale, the write protocols, state machines, indexes,
concurrency rules and retention policies. **Keep it in sync with every migration.**

## Migrations

| Migration | Kind | Contents |
|---|---|---|
| `20261009191030_init` | Generated by Prisma, plus two extensions at the top | `CREATE EXTENSION pg_trgm` (trigram name/email search) and `btree_gist` (exclusion constraints on ranges); every enum, table, foreign key, unique and plain index declared in `schema.prisma`, including the GIN trigram indexes on `users`. |
| `20261009191031_integrity_constraints` | Hand-written SQL | Reference data (`currencies`), every CHECK constraint, partial unique index, exclusion constraint, guard trigger, deferred constraint trigger and the `ledger_account_balances` view described under [Invariants](#invariants). |
| `20261010120000_fix_referral_modify_guard` | Hand-written fix-forward | Replaces `app_referral_modify_guard()`. The original evaluated `NEW."child_user_id"` for every guarded table, so any UPDATE/DELETE on `referral_paths` inside an audited correction failed with `42703` (record "new" has no field "child_user_id"), making corrections impossible. The cycle check now runs only for UPDATEs of `referral_relationships`; PL/pgSQL resolves record fields lazily per branch. Covered by `test/db-invariants.int-spec.ts` and the sponsor-correction suites. |
| `20261010150000_program_cancel_scheduled` | Hand-written | Replaces `app_programs_guard()` unchanged except for one transition: `SCHEDULED → ARCHIVED` is now allowed, so a published program can be withdrawn (`POST /admin/programs/{id}/cancel`) before its start date. Safe because enrollments and sales both require a program that is or was ACTIVE; `ck_programs_completed_has_end` still requires `ends_at`, which the service sets, and the reason is logged through `app.status_reason`. |

Applied migrations are never edited (Prisma checksums them). Defects are fixed with a new
migration, as above. See [Working with migrations](#working-with-migrations).

## Conventions

| Aspect | Rule |
|---|---|
| Keys | `uuid` primary keys, except `platform_settings.id = 1` (singleton), `currencies.code`, and composite keys on join tables, closure rows and `idempotency_keys (actor_user_id, key)`. |
| Naming | snake_case tables and columns (`@@map` / `@map`). Prefixes: `ck_` CHECK, `uq_` partial unique index, `ex_` exclusion constraint, `ix_` partial/extra index, `trg_` trigger, `app_` SQL function. Prisma-generated names are `<table>_<cols>_key` / `_idx`. |
| Time | `timestamptz(3)`, always UTC. Program dates are displayed in the program's IANA `timezone`. Ranges are half-open `[from, to)`. |
| Money / points | `BIGINT` integer minor units in `*_minor` columns; rates in integer basis points (`*_bps`, 10 000 = 100 %). See [ADR-0004](decisions/0004-integer-minor-units-reward-unit.md). |
| Unit / currency | Every amount-bearing row stores its own `reward_unit` and `currency_code` (programs, calculations, rewards, ledger accounts and entries also store or derive minor units), so history never depends on current settings. |
| Optimistic concurrency | `version int` on `programs` and `platform_settings`, **bumped by the guard trigger** on every UPDATE (the application never writes it). A conditional `WHERE version = $expected` that matches nothing → `409 STALE_VERSION`. |
| Errors | Guards raise SQLSTATE `23001` (`restrict_violation`) or `23514` (`check_violation`); exclusion constraints raise `23P01`. The API maps all three to `409 INVARIANT_VIOLATION` (unique violations → `409 CONFLICT` or a domain code). |
| "Created in this transaction" | `app_created_in_this_tx(xmin)` compares a row's `xmin` with `pg_current_xact_id()`. Code relying on it (registration, corrections) must not use SAVEPOINTs: in Prisma 7, `tx.$transaction(...)` inside an interactive transaction opens one. |
| Deferred checks | Cross-row invariants are `CONSTRAINT TRIGGER … DEFERRABLE INITIALLY DEFERRED` (or a deferrable exclusion constraint), so a use case can build valid state over several statements; they fire at COMMIT, where Prisma surfaces them as a `DriverAdapterError`. |

## Entity overview

### Reference data and settings

| Table | Purpose |
|---|---|
| `currencies` | ISO 4217 code ↔ minor units (INR, USD, EUR, GBP, AED, SGD, AUD, CAD, JPY, NPR, LKR, BDT), seeded by the integrity migration and immutable. Programs and settings reference `(code, minor_units)` with a composite FK, so a currency's minor units can never drift from what a record snapshotted. |
| `platform_settings` | Singleton (`id = 1`): `reward_unit` (MONEY/POINTS), `currency_code` + `currency_minor_units`, `points_label`, `points_per_currency_unit`, `default_reward_budget_bps`, `payouts_enabled` (pinned false), `version`, `updated_by_id`. |

### Identity and access

| Table | Purpose |
|---|---|
| `users` | Account and profile: normalized unique `email`, `status` (ACTIVE / SUSPENDED / DEACTIVATED; PENDING_VERIFICATION is legacy only), argon2id `password_hash`, `password_changed_at`, phone, `avatar_url`, suspension fields, `last_login_at`. Trigram GIN indexes on `full_name` and `email`. |
| `sessions` | One row per session: `token_hash` (SHA-256 of the cookie token), `mfa_method` + `mfa_verified_at` (second factor completed in this session), IP, user agent, `last_seen_at` (idle), `expires_at` (absolute), `revoked_at` + `revoke_reason`. MFA elevation inserts a new row and revokes the old one (`mfa_rotated`). |
| `email_challenges` | One-time codes (EMAIL_VERIFICATION, LOGIN_MFA, PASSWORD_RESET, EMAIL_CHANGE): HMAC `code_hash`, `attempts` / `max_attempts`, `send_count`, `last_sent_at`, `expires_at`, `consumed_at`, `invalidated_at`; `session_id` (the requesting session for LOGIN_MFA, the issuing SUPER_ADMIN session for an admin-triggered PASSWORD_RESET); the **pending registration** payload (`pending_full_name`, `pending_password_hash`, `pending_referral_code_id`) for not-yet-created accounts ([ADR-0010](decisions/0010-deferred-user-creation-anti-squatting.md)). |
| `user_mfa_factors` | TOTP authenticators: AES-256-GCM `secret_enc`, `confirmed_at`, `last_used_step` (replay protection), `revoked_at` ([ADR-0009](decisions/0009-totp-admin-mfa-session-rotation.md)). |
| `roles`, `permissions`, `role_permissions` | RBAC catalogue, seeded from `@app/shared` (`RoleKey`, `Permission`, `ROLE_PERMISSIONS`). |
| `user_roles` | Role grants with `granted_by_id`. |
| `program_admin_assignments` | Scopes PROGRAM_ADMIN users to programs. |
| `idempotency_keys` | `Idempotency-Key` records per actor: route, request hash, IN_PROGRESS/COMPLETED, stored response, `expires_at` ([ADR-0012](decisions/0012-idempotency-key-storage.md)). |

### Catalog and programs

| Table | Purpose |
|---|---|
| `offerings` | Products/services (`kind` PRODUCT/SERVICE). Created INACTIVE; ACTIVE requires an approver. The only things whose sales fund rewards. |
| `programs` | A program over one offering: lifecycle `status`, `starts_at`/`ends_at`, enrollment window, `max_reward_depth` (≤ 10), `late_event_grace_days`, snapshot `reward_unit` + `currency_code` + `currency_minor_units`, `eligibility` JSON, `terms_version`/`terms_text`, `version`, `published_at`, `created_by_id`/`updated_by_id`. |
| `program_status_changes` | Append-only status history written by trigger (from, to, when, who, reason). Used to decide whether a program was ACTIVE at a sale's `occurred_at`. |
| `program_options` | Plans (price in the program currency, billing frequency, duration, renewal policy, active flag, sort order). Never a reward trigger. |
| `program_enrollments` | Member ↔ program ↔ option: immutable `option_snapshot`, `terms_version`, `sponsor_user_id` (attribution snapshot), `status`, `eligibility_status`, coverage `[effective_from, effective_to)`, offline payment record (`payment_reference` unique, amount, recorder, time), `cancelled_at`, `status_reason`. |

### Referral tree

| Table | Purpose |
|---|---|
| `referral_codes` | Codes (8 chars, unambiguous alphabet). `program_id NULL` = the member's global code. |
| `referral_relationships` | Adjacency list: one row per child → sponsor, with `source` (REGISTRATION / ADMIN_CORRECTION), the code used, `registration_ip` (`inet`) and user agent, `attributed_at`. |
| `referral_paths` | Closure table: (ancestor, descendant, depth), including depth-0 self rows. |
| `referral_corrections` | Append-only record of admin sponsor moves (child, previous and new sponsor, reason, performer). Its id authorizes the rewrite. |

### Reward policy

| Table | Purpose |
|---|---|
| `reward_policy_versions` | Versioned, effective-dated rules per program: `trigger_event_types[]`, `max_depth`, `budget_bps` (≤ 5000), optional `max_total_per_event_minor`, `min_event_amount_minor`, `points_per_currency_unit` (snapshot), `ineligible_ancestor_behavior` (FORFEIT/COMPRESS), `rounding_mode`, `requires_approval`, `require_active_enrollment`, `[effective_from, effective_to)`, status DRAFT/PUBLISHED/RETIRED, publisher and timestamps. |
| `reward_rules` | One per (version, level 1..10): FIXED `fixed_amount_minor` or PERCENTAGE `percentage_bps`, optional `cap_minor`. |

### Sales, calculations and rewards

| Table | Purpose |
|---|---|
| `api_clients` | Machine credentials for one program: `key_prefix`, SHA-256 `key_hash`, `last_used_at`, `revoked_at`. |
| `qualifying_events` | Sales of the program's offering credited to a subject member: `type`, `source` (ADMIN_MANUAL / API / WEBHOOK), `external_id` + `revision` (+ `supersedes_event_id`), `request_hash`, `customer_reference`, amount + currency, `occurred_at`, status RECEIVED → PROCESSED / REJECTED, PROCESSED → REVERSED, the bound `policy_version_id`, recorder or API client. |
| `reward_calculations` | Exactly one per processed event: outcome, unit/currency/minor units/points-rate snapshot, `base_minor`, `budget_bps`, `budget_minor`, `total_allocated_minor`, the full `trace` JSON, `engine_version`. Append-only. |
| `rewards` | One per (event, level) and per (event, recipient): amount + unit + currency, status PENDING_APPROVAL → APPROVED → POSTED → REVERSED (+ REJECTED), decision columns (who/when/reason). |

### Ledger

| Table | Purpose |
|---|---|
| `ledger_accounts` | `PLATFORM_REWARD_EXPENSE` (no owner) and `MEMBER_REWARDS_PAYABLE` (one per member), each per unit + currency. |
| `ledger_transactions` | REWARD_POSTING / REWARD_REVERSAL headers: `idempotency_key` (`reward-posting:<rewardId>` / `reward-reversal:<rewardId>`), `reward_id`, `reverses_transaction_id`, `entry_count`, `debit_total_minor`, description, poster. |
| `ledger_entries` | DEBIT/CREDIT lines with `amount_minor > 0`, unit and currency. |
| `ledger_account_balances` (view) | `credits_minor` and `debits_minor` per account. Member balance = credits − debits. |

### Audit, messaging, risk

| Table | Purpose |
|---|---|
| `audit_logs` | Append-only: actor + roles, action, resource, `program_id` (for scoped views), allow-listed masked `before`/`after`, reason, request id, IP. |
| `notifications` | In-app notifications per user; `source_key` (outbox message id) de-duplicates at-least-once delivery. |
| `outbox_messages` | Transactional outbox ([ADR-0006](decisions/0006-transactional-outbox-bullmq.md)): topic, payload, `dedupe_key`, status, attempts, `available_at`, `locked_at`, `last_error`. |
| `member_flags` | Fraud signals and manual flags (OPEN / RESOLVED / DISMISSED), `dedupe_key` for heuristic upserts. Advisory only. |

## Invariants

Everything in this section lives in `20261009191031_integrity_constraints` (as amended by
`20261010120000_fix_referral_modify_guard`), unless marked "(Prisma)". The application validates
first and returns friendly errors; these constraints catch races, bugs and manual SQL. Each guard
is proven by an attack case in `apps/api/test/db-invariants.int-spec.ts` or a slice suite.

Shared helpers: `app_forbid_modification()` raises `restrict_violation` on any UPDATE/DELETE and
backs every **append-only** trigger; `app_created_in_this_tx(xmin)` (see Conventions).

### Reference data and platform settings

| Constraint / trigger | Rule | Rationale |
|---|---|---|
| `ck_currencies_code`, `ck_currencies_minor_units` | `^[A-Z]{3}$`, `0..4` | ISO-shaped codes, sane scaling. |
| `trg_currencies_guard` | No DELETE; `code` and `minor_units` never change | Every program, calculation and settings row snapshotted a (code, minor units) pair through the composite FK; changing it would re-scale history. |
| `ck_platform_settings_singleton` | `id = 1` | Exactly one settings row. |
| `ck_platform_settings_points_rate` | `1..1 000 000` | Positive, bounded POINTS conversion (no overflow in `amount × rate`). |
| `ck_platform_settings_budget` | `default_reward_budget_bps 1..5000` | The draft default can never exceed the 50 % cap ([ADR-0007](decisions/0007-sale-funded-rewards-budget-cap.md)). |
| `ck_platform_settings_points_label`, `ck_platform_settings_version` | non-blank, `≥ 1` | Shown next to every points amount; concurrency token sanity. |
| **`ck_platform_settings_no_payouts`** | `payouts_enabled = false` | Compliance guardrail: real-money payouts need a reviewed migration after legal, KYC and payment-provider approval. |
| `trg_platform_settings_guard` | Currency change refused while a SCHEDULED/ACTIVE/PAUSED program uses another currency; `version := old + 1` | Live programs price plans and sales in their snapshotted currency; the trigger owns the version bump so it is incremented exactly once. |

### Users, sessions, challenges, MFA, roles, idempotency keys

| Constraint / trigger | Rule | Rationale |
|---|---|---|
| `ck_users_email_normalized` | `email = lower(btrim(email))`, `@` after position 1 | Uniqueness is on the normalized value. |
| `ck_users_full_name` | non-blank | Display names derive from it. |
| `ck_users_active_verified` | ACTIVE ⇒ `email_verified_at` set | Accounts are created at verification ([ADR-0010](decisions/0010-deferred-user-creation-anti-squatting.md)); an unverified ACTIVE user would mean someone bypassed it. |
| `ck_sessions_expiry` | `expires_at > created_at` | No born-expired sessions. |
| `ck_sessions_mfa` | `mfa_verified_at` and `mfa_method` both set or both NULL | An elevated session always records how it was elevated. |
| `ck_email_challenges_attempts` | `0 ≤ attempts ≤ max_attempts` | The 5-attempt limit holds even under concurrent verifies (the increment fails). |
| `ck_email_challenges_send_count`, `ck_email_challenges_expiry` | `≥ 1`, `expires_at > created_at` | A challenge exists only once a code was sent, with a positive TTL. |
| `ck_email_challenges_mfa_session` | LOGIN_MFA ⇒ `session_id` and `user_id` set | A login code elevates only the session that requested it. |
| `ck_email_challenges_pending_payload` | Pending fields all NULL, or EMAIL_VERIFICATION with `user_id IS NULL` and name + password hash present | Pending registrations exist only for addresses without an account, and nowhere else. |
| `uq_email_challenges_one_open` | Partial unique `(email, purpose) WHERE consumed_at IS NULL AND invalidated_at IS NULL` | One open code per address and purpose: issuing a new one must invalidate the old one first, in the same transaction. |
| `uq_mfa_factors_one_active` | Partial unique `(user_id, kind) WHERE revoked_at IS NULL` | At most one live authenticator per user (pending or confirmed). |
| `ck_user_roles_not_self_granted` | `granted_by_id <> user_id` | Nobody grants roles to themselves. |
| `trg_user_roles_keep_super_admin`, `trg_users_keep_super_admin` → `app_assert_super_admin_exists()` (deferred) | At COMMIT at least one ACTIVE SUPER_ADMIN remains after a role DELETE/UPDATE or a user leaving ACTIVE | The platform can never lock itself out. The function locks the SUPER_ADMIN `roles` row `FOR UPDATE`, which serializes concurrent removals (no write skew). |
| `ck_idempotency_keys_expiry`, `ck_idempotency_keys_completed`, `ck_idempotency_keys_hash` | `expires_at > created_at`; COMPLETED ⇒ `response_status` set; hash = 64 hex | A completed key can always replay its response; hashes are well-formed. |

### Offerings, programs, options

| Constraint / trigger | Rule | Rationale |
|---|---|---|
| `ck_offerings_name` | non-blank | |
| `ck_offerings_approved` | ACTIVE ⇒ `approved_by_id` and `approved_at` set | Only approved products/services fund rewards; the approver is on record. |
| `ck_programs_code_slug` | `^[a-z0-9]+(-[a-z0-9]+)*$` | URL-safe, stable identifiers. |
| `ck_programs_dates`, `ck_programs_enrollment_window`, `ck_programs_enrollment_within_program` | `ends_at > starts_at`; `enrollment_closes_at > enrollment_opens_at`; when `ends_at` is set the window opens before it and closes no later | Positive durations; no enrollment after a program has ended. |
| `ck_programs_max_depth`, `ck_programs_grace` | `1..10`, `0..365` days | Hard ceiling for every policy version's depth; bounded late-sale window. |
| `ck_programs_version`, `ck_programs_published_at` | `≥ 1`; non-DRAFT ⇒ `published_at` set | |
| `ck_programs_completed_has_end` | COMPLETED/ARCHIVED ⇒ `ends_at` set | The late-sale window is computed from `ends_at`. |
| `trg_programs_insert_guard` | Programs are inserted as DRAFT | Publication goes through the state machine and its checks. |

| `trg_programs_forbid_delete` | Only DRAFT programs can be deleted | Published programs are completed and archived, never deleted. |
| `trg_programs_log_status` → `program_status_changes` | Every INSERT and status change writes a history row with `updated_by_id` as the actor and `current_setting('app.status_reason', true)` as the reason (set per transaction with `set_config(..., true)`) | The intake asks "was the program ACTIVE at `occurred_at`?"; the history cannot be skipped because the trigger writes it. |
| `trg_program_status_changes_append_only` | UPDATE/DELETE refused at trigger depth 0 | History is immutable; FK cascades (deleting a DRAFT program) still work. |
| `ck_program_options_price`, `ck_program_options_duration`, `ck_program_options_name` | `price_minor ≥ 0`, `1..3660` days, non-blank | Free plans allowed; frequency/duration consistency is validated by the API. |
| `trg_program_options_guard` | Option currency = program currency (`23514`); price, duration, frequency and program of an option with enrollments never change | Members agreed to those terms; renewals use a new option. |

| `ck_enrollments_active_has_period`, `ck_enrollments_eligible_needs_period` | ACTIVE/EXPIRED ⇒ both dates; ELIGIBLE ⇒ `effective_from` | The engine's eligibility test `effective_from ≤ occurred_at < effective_to` always has its inputs. |
| `ck_enrollments_cancelled_at` | CANCELLED ⇒ `cancelled_at` | Sales before `cancelled_at` still count. |
| `ck_enrollments_payment_amount`, `ck_enrollments_payment_complete` | amount `≥ 0`; reference, amount and recorded-at all set or all NULL | Payment records are complete or absent. |
| **`ck_enrollments_paid_activation`** | A paid option (`option_snapshot.priceMinor > 0`) is ACTIVE/EXPIRED only with a `payment_reference` | Nobody becomes eligible on a paid plan without a recorded payment. |
| `program_enrollments_payment_reference_key` (Prisma) | Unique `payment_reference` | One payment activates one enrollment. |
| `trg_enrollments_insert_guard` | Inserted PENDING or ACTIVE; program ACTIVE with an open window (row read `FOR SHARE`, so it serializes with pause/complete); option active and belonging to the program; member ACTIVE + verified; coverage not starting in the past | The enrollment preconditions hold even for direct SQL or a race with a lifecycle change. |
| `trg_enrollments_guard` → `app_enrollments_guard()` | No DELETE; snapshot, option, member, program, terms version, sponsor and `created_at` immutable; a recorded payment is immutable; terminal statuses (CANCELLED, EXPIRED, REJECTED) never change; [enrollment state machine](#enrollment); EXPIRED only once `effective_to` has passed; `effective_from` frozen once set and never set in the past; `effective_to` frozen except a cancellation that shortens it, never into the past | The enrollment documents what the member agreed to, who referred them and the coverage that made them reward-eligible; rewritten coverage would retroactively change eligibility. |

### Referral tree

The [write protocol](#write-protocol-db-enforced) is enforced by these objects; the
helpers read the session's own advisory locks from `pg_locks`.

| Constraint / trigger | Rule | Rationale |
|---|---|---|
| `uq_referral_codes_global_per_user` | Partial unique `(user_id) WHERE program_id IS NULL AND is_active` | One active global code per member; old codes stay for history. |
| `ck_referral_codes_format` | `^[A-Z0-9]{6,16}$` | Upper-case, URL-safe codes. |
| `ck_referral_relationships_not_self` | `child_user_id <> sponsor_user_id` | No self-referral. |
| `ck_referral_relationships_code_source` | REGISTRATION ⇒ `referral_code_id` set | Organic attribution always names the code used. |
| `referral_relationships_child_user_id_key` (Prisma) | Unique `child_user_id` | One sponsor per member. |
| `ck_referral_paths_depth`, `ck_referral_paths_self_row` | `0 ≤ depth ≤ 1000`; `(depth = 0) = (ancestor = descendant)` | Exactly the self rows have depth 0, so a cycle can never appear as a self-loop at depth > 0. |
| `uq_referral_paths_descendant_depth` (Prisma) | Unique `(descendant_id, depth)` | One ancestor per level: the structure is a tree, not a DAG. |
| `app_referral_lock_mode()` | `'exclusive'` / `'shared'` / NULL for advisory lock `(7301, 1)` held by this backend | Lets triggers verify the caller took the tree lock. |
| `app_in_referral_correction()` | True only if `app.referral_correction_id` names a `referral_corrections` row **inserted in this transaction** and the exclusive tree lock is held | A setting leaked on a pooled connection is harmless; there is no "magic flag" that opens the tree. |
| `trg_referral_relationships_insert_guard` | Outside a correction: tree lock held (any mode), child created in this transaction, child's self row created in this transaction, child has no descendants yet, `source = REGISTRATION`, code active and owned by the ACTIVE + verified sponsor. Inside a correction: cycle check | Attribution happens once, in the transaction that creates the member, from a valid code. Nobody can attach an existing member to a sponsor later. |
| `trg_referral_paths_insert_guard` | Outside a correction: tree lock held, descendant created in this transaction, and for depth > 0 its self row was created in this transaction first | Closure rows cannot be fabricated for existing members. |
| `trg_referral_relationships_guard`, `trg_referral_paths_guard` → `app_referral_modify_guard()` | UPDATE/DELETE only inside a correction; relationship UPDATEs are cycle-checked (fixed by `20261010120000_fix_referral_modify_guard`) | Attribution decides who earns rewards. It changes only through the audited correction protocol. |
| `trg_referral_paths_consistent`, `trg_referral_relationships_consistent` → `app_referral_assert_consistent()` (deferred) | At COMMIT every touched member has its depth-0 row, and its closure rows equal its sponsor's rows shifted by one | The closure table can never disagree with the adjacency list, whatever order the statements ran in. |
| `ck_referral_corrections_not_self`, `ck_referral_corrections_reason` | `child <> new_sponsor`; reason ≥ 10 non-blank chars | Every correction is justified. |
| `ck_referral_corrections_sod` | Performer ≠ new sponsor, ≠ moved member, ≠ previous sponsor | Segregation of duties ([ADR-0011](decisions/0011-db-enforced-segregation-of-duties.md)). |
| `trg_referral_corrections_insert_guard` | Exclusive tree lock held; performer is not an upline of the new sponsor; new sponsor not inside the moved subtree | No moving members under one's own downline; no cycles. |
| `trg_referral_corrections_append_only` | append-only | Corrections are an audit trail. |

### Reward policy versions and rules

## State machines

Every arrow not drawn is refused by a trigger (`23001` → `409 INVARIANT_VIOLATION`); the services
report the same cases first as `409 INVALID_STATE_TRANSITION`.

### Program

```
            publish (startsAt ahead)            scheduler at startsAt
   DRAFT ─────────────────────────────▶ SCHEDULED ───────────────────────┐
     │                                      │                            ▼
     └──────── publish (startsAt passed) ───┼──────────────────────▶  ACTIVE ◀──── resume ────┐
                                            │                            │                    │
                                            │            pause (reason)  └────▶ PAUSED ───────┘
                                            │                            │          │
                       complete (manual, endsAt := now if later)         ▼          ▼
                       or scheduler at endsAt                   ───▶  COMPLETED ◀───┘
                                            │                            │ archive
                                            │ cancel (reason,            ▼
                                            └─ before startsAt) ────▶ ARCHIVED   (read-only)
```

- Inserted as DRAFT only; never back to DRAFT; only DRAFT can be deleted.
- **Cancel** `SCHEDULED → ARCHIVED` withdraws a published program before it starts (API: reason
  required, only while `starts_at` is ahead; the service sets `ends_at` because ARCHIVED requires
  it). A SCHEDULED program never was ACTIVE, so it has no enrollments or sales. Added by migration
  `20261010150000_program_cancel_scheduled`.
- Leaving DRAFT requires an ACTIVE offering (DB) plus ≥ 1 active option, valid dates and ≥ 1
  PUBLISHED policy version (API publish checks).
- Every transition writes `program_status_changes` (actor from `updated_by_id`, reason from
  `app.status_reason`; the scheduler is `changed_by = NULL`).
- Frozen after DRAFT: code, offering, unit, currency, minor units, max depth. Frozen once started:
  `starts_at`. Frozen once COMPLETED: `ends_at`, enrollment close, grace days.

### Enrollment

```
 (insert) ──▶ PENDING ──activate (payment)──▶ ACTIVE ──scheduler at effectiveTo──▶ EXPIRED
   │             │ reject                       │ cancel (effectiveTo shortened)
   │             ▼                              ▼
   │          REJECTED                       CANCELLED
   │             (PENDING ──cancel──▶ CANCELLED)
   └── free plan: inserted ACTIVE directly
```

CANCELLED, EXPIRED and REJECTED are terminal.

### Reward policy version

```
 (insert) ──▶ DRAFT ──publish at T──▶ PUBLISHED ──retire──▶ RETIRED (frozen)
                │ delete                   │ effective_to may only be closed / shortened
                ▼                          ▼
             (gone)              (closed at T by the next publish)
```

### Qualifying event

```
 (insert) ──▶ RECEIVED ──engine──▶ PROCESSED ──refund / chargeback──▶ REVERSED
   │             │ engine or intake rejects
   │             ▼
   └──────────▶ REJECTED        (REJECTED / REVERSED may be superseded by revision + 1)
```

### Reward

```
 (insert) ──▶ PENDING_APPROVAL ──approve──▶ APPROVED ──post (ledger)──▶ POSTED ──reverse (ledger)──▶ REVERSED
                    │ reject                   │ reject
                    ▼                          ▼
                 REJECTED ◀────────────────────┘
 (auto-approving policy, non-manual sale: inserted APPROVED and posted in the same transaction)
```

## Referral tree (closure table) and its write protocol

Design and alternatives: [ADR-0003](decisions/0003-referral-tree-closure-table.md).
`referral_relationships` is the adjacency list (who sponsored whom). `referral_paths` holds every
(ancestor, descendant, depth) pair, including depth-0 self rows.

```
A ─┬─ B ─┬─ D
   │     └─ E ── G
   └─ C ── F
```

`referral_paths` for G: `(G,G,0) (E,G,1) (B,G,2) (A,G,3)`.

### Write protocol (DB-enforced)

Both writers use advisory lock `(7301, 1)` (helpers in `apps/api/src/common/prisma/referral-tree-lock.ts`),
run in one transaction and **never use savepoints**.

**Registration** (the transaction that verifies the email code and creates the user; implemented
by `ReferralsService.attachNewMember`):

```sql
INSERT INTO users (...) VALUES (...);                         -- 1. the member, ACTIVE + verified
SELECT pg_advisory_xact_lock_shared(7301, 1);                 -- 2. shared tree lock
INSERT INTO referral_paths (ancestor_id, descendant_id, depth)
VALUES ($child, $child, 0);                                   -- 3. self row FIRST
INSERT INTO referral_relationships
  (id, child_user_id, sponsor_user_id, referral_code_id, source, registration_ip, registration_user_agent)
VALUES (gen_random_uuid(), $child, $sponsor, $code_id, 'REGISTRATION', $ip, $ua);   -- 4. if sponsored
INSERT INTO referral_paths (ancestor_id, descendant_id, depth)
SELECT ancestor_id, $child, depth + 1
FROM referral_paths WHERE descendant_id = $sponsor;           -- 5. ancestor rows
INSERT INTO referral_codes (...);                             -- the member's own code
```

The insert guards refuse any of these rows unless the tree lock is held, the user was created in
this transaction and its self row came first; the relationship also needs an active code owned by
an ACTIVE, verified sponsor. Registrations hold the lock in shared mode, so they never block each
other.

**Correction** (SUPER_ADMIN, `referrals:correct`; implemented by `SponsorCorrectionService`):

```sql
SELECT pg_advisory_xact_lock(7301, 1);                        -- 1. exclusive tree lock FIRST
-- 2. re-check every rule under the lock (cycle, SoD, sponsor ACTIVE + verified, no RECEIVED sales)
INSERT INTO referral_corrections (id, child_user_id, previous_sponsor_id, new_sponsor_id, reason, performed_by_id)
VALUES ($cid, $m, $old, $s, $reason, $actor);                 -- 3. authorizes the rewrite
SET LOCAL app.referral_correction_id = '<$cid>';              -- 4. (set_config(..., true))

UPDATE referral_relationships                                 -- 5. adjacency (INSERT if $m was a root)
   SET sponsor_user_id = $s, source = 'ADMIN_CORRECTION', referral_code_id = NULL, attributed_at = now()
 WHERE child_user_id = $m;

DELETE FROM referral_paths p                                  -- 6. detach: old strict ancestors × subtree
USING referral_paths up, referral_paths sub
WHERE up.descendant_id = $m AND up.depth > 0
  AND sub.ancestor_id = $m
  AND p.ancestor_id = up.ancestor_id AND p.descendant_id = sub.descendant_id;

INSERT INTO referral_paths (ancestor_id, descendant_id, depth) -- 7. attach: new upline × subtree
SELECT up.ancestor_id, sub.descendant_id, up.depth + sub.depth + 1
FROM referral_paths up
JOIN referral_paths sub ON sub.ancestor_id = $m
WHERE up.descendant_id = $s;
-- + AuditService.record(tx, { action: 'referral.correct', ... }) in the same transaction
```

At COMMIT the deferred consistency triggers re-check every touched member against its sponsor
chain. Past rewards are never recalculated; only calculations made afterwards see the new
placement. The reward engine takes the tree lock in shared mode while it reads an upline, so it
waits for an in-flight correction.

### Read patterns

Member-facing reads cap depth at 10 and select only privacy-safe columns (business rules §6):
display name (first name + last initial), depth, join date, status bucket, eligible-enrollment
flag, direct-referral count. Never email, phone, prices, rewards or sale amounts.

```sql
-- Direct children (depth 1), keyset-paginated on the adjacency index.
SELECT r.child_user_id, r.attributed_at
FROM referral_relationships r
WHERE r.sponsor_user_id = $member
  AND (r.attributed_at, r.child_user_id) > ($cursor_at, $cursor_id)
ORDER BY r.attributed_at, r.child_user_id
LIMIT $limit;

-- Ancestors (upline), nearest first: the reward engine (FORFEIT: up to max_depth; COMPRESS: up to 50).
SELECT p.ancestor_id, p.depth
FROM referral_paths p
WHERE p.descendant_id = $subject AND p.depth BETWEEN 1 AND $max_depth
ORDER BY p.depth;

-- Team size per depth (+ active / eligible counts).
SELECT p.depth, count(*) AS members,
       count(*) FILTER (WHERE u.status = 'ACTIVE') AS active
FROM referral_paths p JOIN users u ON u.id = p.descendant_id
WHERE p.ancestor_id = $member AND p.depth BETWEEN 1 AND 10
GROUP BY p.depth ORDER BY p.depth;

-- Search within a team by name (pg_trgm GIN index prefilters; % _ \ escaped in $term).
SELECT p.descendant_id, p.depth
FROM referral_paths p JOIN users u ON u.id = p.descendant_id
WHERE p.ancestor_id = $member AND p.depth BETWEEN 1 AND 10
  AND u.full_name ILIKE '%' || $term || '%'
ORDER BY p.depth LIMIT 25;

-- Is $x inside $y's subtree? (cycle check, SoD, admin scoping)
SELECT EXISTS (SELECT 1 FROM referral_paths WHERE ancestor_id = $y AND descendant_id = $x);
```

### Consistency check

The deferred triggers enforce this per touched member at COMMIT. The full-table version below
returns zero rows when consistent; use it after a restore or in investigations:

```sql
WITH RECURSIVE chain AS (
  SELECT r.sponsor_user_id AS ancestor_id, r.child_user_id AS descendant_id, 1 AS depth
  FROM referral_relationships r
  UNION ALL
  SELECT r.sponsor_user_id, c.descendant_id, c.depth + 1
  FROM chain c JOIN referral_relationships r ON r.child_user_id = c.ancestor_id
  WHERE c.depth < 1000
)
(SELECT ancestor_id, descendant_id, depth FROM chain
 EXCEPT SELECT ancestor_id, descendant_id, depth FROM referral_paths WHERE depth > 0)
UNION ALL
(SELECT ancestor_id, descendant_id, depth FROM referral_paths WHERE depth > 0
 EXCEPT SELECT ancestor_id, descendant_id, depth FROM chain)
UNION ALL
(SELECT id, id, 0 FROM users
 EXCEPT SELECT ancestor_id, descendant_id, depth FROM referral_paths WHERE depth = 0);
```

## Ledger shape rules

The ledger records reward **liabilities** only (no payouts). Each reward has at most one posting
and one reversal, and the deferred triggers accept only these two shapes:

```
REWARD_POSTING   idempotency_key = 'reward-posting:<rewardId>'   entry_count = 2   debit_total = A
  DEBIT   PLATFORM_REWARD_EXPENSE        (unit U, currency C)   A
  CREDIT  MEMBER_REWARDS_PAYABLE[recipient] (unit U, currency C)   A

REWARD_REVERSAL  idempotency_key = 'reward-reversal:<rewardId>'  reverses_transaction_id = <posting>
  every entry of the posting, same account and amount, opposite direction (exact mirror)
```

`A`, `U`, `C` are the reward's amount, unit and currency. Rules:

1. Both entries are written in the **same transaction** as the reward's status change
   (`LedgerService.postReward` moves the reward to POSTED, `reverseReward` to REVERSED); callers do
   not change the status themselves.
2. Accounts are created on demand with `INSERT … ON CONFLICT DO NOTHING`, then re-selected.
3. The header (`entry_count`, `debit_total_minor`) is checked against the entries at COMMIT, so an
   entry appended later in another transaction fails.
4. Balances: member payable = credits − debits (credit-normal); platform expense = debits −
   credits (debit-normal). Earned to date for a member = Σ over their payable accounts.
5. Unit and currency never mix: each entry must match its account, and each transaction balances
   per (unit, currency).

## Concurrency strategy

Binding for every service that writes these tables.

1. **One use case = one transaction** (`prisma.runInTransaction`). Audit rows and outbox messages
   are written inside it. Nothing external (email, HTTP) happens inside a transaction.
2. **Unique constraints arbitrate races.** Insert, then map the violation to the domain error:
   one PENDING enrollment, payment references, sale revisions, one calculation per event, one
   reward per level/recipient, one posting/reversal per reward, ledger account get-or-create, user
   email, outbox `dedupe_key`, notification `source_key`, open flag dedupe key, idempotency keys.
3. **Advisory locks** (transaction-scoped):

   | Lock | Mode | Taken by | Purpose |
   |---|---|---|---|
   | `(7301, 1)` | shared | registration, reward engine (while reading an upline) | Never block each other; wait for a correction |
   | `(7301, 1)` | exclusive | sponsor correction (first statement) | Rewrites a subtree while no registration copies a stale upline |
   | `(7302, hashtext('<purpose>:<email>'))` | exclusive | one-time code issuance | One open challenge per address and purpose, history-derived limits |
   | `(7302, hashtext('<userId>:<programId>'))` | exclusive | enroll, activate, cancel | Serializes coverage computation per member and program |
   | `(7302, hashtext('<programId>'))` | exclusive | policy publish / retire / timeline edits | Then every version row of the program `FOR UPDATE` |

   The 7302 keys share a class; a hash collision only adds serialization.
4. **Row locks for state machines.** The engine locks the event `FOR UPDATE` and skips unless
   RECEIVED. Approve/reject/reverse lock the **event `FOR SHARE`, then the reward `FOR UPDATE`**;
   event reversal UPDATEs the event first (conflicting with those share locks) and then locks its
   rewards, so approval and reversal serialize in one order. Role removals and suspensions lock the
   SUPER_ADMIN `roles` row (the same row the deferred trigger locks). Enrollment and event inserts
   read the program `FOR SHARE`, so they serialize with pause/complete.
5. **Optimistic concurrency** for edits of programs and settings (`version`, bumped by trigger).
6. **Policy publication** closes the open version and publishes the new one in one transaction;
   the deferred exclusion constraint rejects any overlap at COMMIT.
7. **Ledger** entries are written in the same transaction as the reward status change; deferred
   checks validate shape, balance and status coupling at COMMIT.
8. **Outbox relay** claims rows with `FOR UPDATE SKIP LOCKED` (safe with several workers) and
   reclaims PROCESSING rows locked for more than 5 minutes.
9. **Isolation:** READ COMMITTED plus the locks and constraints above. `runInTransaction({ retries })`
   re-runs idempotent work on `40001`/`40P01`; serialization failures otherwise surface as
   `409 CONFLICT` with `details.retryable`.
10. **Idempotent HTTP mutations** store the key and response in `idempotency_keys`
    ([ADR-0012](decisions/0012-idempotency-key-storage.md)).

## Deletion and retention policies

| Data | Policy |
|---|---|
| Users | **Never hard-deleted** (closure rows, events, rewards, ledger and audit reference them with RESTRICT). Admins suspend/reactivate; `DEACTIVATED` is terminal. Privacy erasure, if required, means anonymizing PII columns, never deleting rows. |
| Sessions | Revoked on logout, password/email change, MFA rotation, suspension and role changes. `auth-session-cleanup` (daily 03:41) deletes rows expired or revoked more than 30 days ago. |
| Email challenges | `auth-challenge-cleanup` (every 15 min) scrubs pending registration payloads of challenges consumed, invalidated or expired more than 24 h ago, and deletes rows older than 30 days. No raw code is ever stored. |
| MFA factors | Revoked (kept) on reset; deleted only with their user. |
| Idempotency keys | Expire after 24 h; `idempotency-keys-cleanup` (hourly) deletes them. |
| Roles / grants | Changed by SUPER_ADMIN (audited); the last ACTIVE SUPER_ADMIN cannot be removed. Catalogue rows are seed-managed. |
| Offerings | Deactivated; deletable only while INACTIVE and unused. |
| Programs | DRAFT: deletable (cascades options, draft versions, assignments, status history). Otherwise complete → archive, never delete (trigger). |
| Program options | Deactivated; terms frozen once used; price change = new option. |
| Enrollments | Never deleted; terminal statuses are final. |
| Referral relationships / paths | Never deleted except inside the audited correction protocol. Corrections are append-only. |
| Policy versions / rules | DRAFT deletable (rules cascade). PUBLISHED/RETIRED immutable, never deleted. |
| Qualifying events | Never deleted. Refunds and chargebacks are reversals; re-records are new revisions. |
| Calculations / rewards | Never deleted. Rejected and reversed rewards stay as history. |
| Ledger | Append-only, never deleted. Corrections are compensating transactions. |
| Audit logs | Append-only, never deleted by the application. Archive per the retention policy agreed with legal (suggest ≥ 7 years for financial records). |
| Notifications | Deleted with their user. May be purged after 180 days once read. |
| Outbox messages | `outbox-cleanup` (daily 03:17) deletes SENT rows older than 14 days; DEAD rows are kept for investigation. OTP ciphertext is scrubbed when a message is SENT/DEAD; `outbox-otp-expiry` (every 15 min) gives up undelivered OTP emails older than an hour. |
| Member flags | Never deleted; resolved or dismissed with a note. |

## Working with migrations

- Never edit an applied migration. Fix forward with a new one (as
  `20261010120000_fix_referral_modify_guard` does).
- Never run `prisma migrate dev` non-interactively (it hangs and can reset data) or `prisma db push`.
  Create migrations from the schema diff:

  ```bash
  cd apps/api
  mkdir -p prisma/migrations/$(date -u +%Y%m%d%H%M%S)_<name>
  corepack pnpm exec prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script \
    > prisma/migrations/<that folder>/migration.sql
  corepack pnpm db:deploy
  ```

- Hand-written invariant SQL goes into its own migration. Add a row to [Invariants](#invariants),
  an attack case to `test/db-invariants.int-spec.ts`, and update
  [business-rules.md](business-rules.md) if a rule changes. Never weaken a trigger to make a use
  case pass; fix the use case.
- `CREATE INDEX CONCURRENTLY` cannot run inside a transaction block: put it alone in a migration.
- Deployment, backups and rollback: [deployment.md §7](deployment.md#7-database-migrations).
