PostgreSQL 17. The schema lives in `apps/api/prisma/schema.prisma`. Migrations are in
`apps/api/prisma/migrations/`:

- `…_init` is generated by Prisma;
- `…_integrity_constraints` is hand-written SQL for everything Prisma cannot express
  ([ADR-0002](decisions/0002-prisma-with-raw-sql-invariants.md)).

This document is the catalogue of entities, invariants, query patterns, indexes, concurrency rules
and deletion policies. **Keep it in sync with every migration.**

## Conventions

| Aspect | Rule |
|---|---|
| Keys | `uuid` primary keys (`@default(uuid())`), except `platform_settings.id = 1` (singleton) and composite keys on join tables / closure rows. |
| Naming | snake_case tables and columns (`@@map` / `@map`). Constraint prefixes: `ck_` CHECK, `uq_` unique, `ex_` exclusion, `trg_` trigger, `app_` functions. |
| Time | `timestamptz(3)`, always UTC. Program dates are displayed in the program's IANA `timezone`. |
| Money / points | `BIGINT` integer minor units in `*_minor` columns; rates in integer basis points (`*_bps`). See [ADR-0004](decisions/0004-integer-minor-units-reward-unit.md). |
| Unit / currency | Every amount-bearing row stores its own `reward_unit` and `currency_code` (`^[A-Z]{3}$`), so history never depends on current settings. |
| Enums | PostgreSQL enums generated from Prisma enums (e.g. `"RewardStatus"`). |
| Optimistic concurrency | `version int` on `programs` and `platform_settings`, incremented on every update. A stale `version` → `409 STALE_VERSION`. |
| Errors | Trigger violations raise SQLSTATE `23001` (`restrict_violation`), and ledger currency/balance violations raise `23514` (`check_violation`). The API maps both, like other constraint violations, to `409 INVARIANT_VIOLATION` (unique violations → `409 CONFLICT` or a domain code). |

## Entity overview

### Settings

| Table | Purpose |
|---|---|
| `platform_settings` | Singleton (`id = 1`). `reward_unit` (MONEY/POINTS), `currency_code` + `currency_minor_units`, `points_label`, `points_per_currency_unit`, `default_reward_budget_bps`, `payouts_enabled` (must stay false), `version`. |

### Identity and access

| Table | Purpose |
|---|---|
| `users` | Account and profile. Normalized unique `email`, `status` (PENDING_VERIFICATION / ACTIVE / SUSPENDED / DEACTIVATED), argon2id `password_hash`, lockout counters (`failed_login_count`, `locked_until`), suspension fields. |
| `sessions` | One row per login. `token_hash` (SHA-256 of the cookie token), `mfa_verified`, `expires_at` (absolute), `last_seen_at` (idle), `revoked_at` + `revoke_reason`, IP and user agent. |
| `email_challenges` | One-time codes (EMAIL_VERIFICATION, LOGIN_MFA, PASSWORD_RESET, EMAIL_CHANGE). HMAC `code_hash`, `attempts` / `max_attempts`, `send_count`, `last_sent_at`, `expires_at`, `consumed_at`, `invalidated_at`. |
| `roles`, `permissions`, `role_permissions` | RBAC catalogue, seeded from `@app/shared` (`RoleKey`, `Permission`, `ROLE_PERMISSIONS`). |
| `user_roles` | Role grants (`granted_by_id`). |
| `program_admin_assignments` | Scopes PROGRAM_ADMIN users to programs. |

### Catalog and programs

| Table | Purpose |
|---|---|
| `offerings` | Approved products/services (`kind` PRODUCT/SERVICE, `status`). The only things whose sales fund rewards. |
| `programs` | Program over one offering. Lifecycle `status`, dates and enrollment window, `max_reward_depth` (≤ 10), snapshot `reward_unit` + `currency_code`, `eligibility` JSON, terms (`terms_version`, `terms_text`), `version`, `published_at`. |
| `program_options` | Plans for the offering (price, billing frequency, duration, renewal policy, active flag). Never a reward trigger. |
| `program_enrollments` | Member ↔ program ↔ option. Immutable `option_snapshot`, `terms_version` and `sponsor_user_id` (attribution snapshot), `status`, `eligibility_status`, `effective_from` / `effective_to`. |

### Referral tree

| Table | Purpose |
|---|---|
| `referral_codes` | Codes (8 chars, Crockford-style). `program_id NULL` = the member's global code. |
| `referral_relationships` | Adjacency list: one row per child → sponsor, with `source` (REGISTRATION / ADMIN_CORRECTION) and the code used. |
| `referral_paths` | Closure table: (ancestor, descendant, depth), including depth-0 self rows. |
| `referral_corrections` | Append-only record of admin sponsor moves (previous / new sponsor, reason, actor). |

### Reward policy

| Table | Purpose |
|---|---|
| `reward_policy_versions` | Versioned, effective-dated rules per program: `trigger_event_types[]`, `max_depth`, `budget_bps` (≤ 5000), optional `max_total_per_event_minor` / `min_event_amount_minor`, `ineligible_ancestor_behavior` (FORFEIT/COMPRESS), `rounding_mode`, `requires_approval`, `require_active_enrollment`, `[effective_from, effective_to)`, status DRAFT/PUBLISHED/RETIRED. |
| `reward_rules` | One per (version, level 1..10): FIXED `fixed_amount_minor` or PERCENTAGE `percentage_bps`, optional `cap_minor`. |

### Events and rewards

| Table | Purpose |
|---|---|
| `qualifying_events` | Sales of an offering credited to a subject member. Idempotent on `(source, external_id)`. Status RECEIVED → PROCESSED / REJECTED, PROCESSED → REVERSED. |
| `reward_calculations` | Exactly one per event: `budget_minor`, `total_allocated_minor`, full `trace` JSON, `engine_version`. Append-only. |
| `rewards` | One per (event, level), and one per (event, recipient). Status PENDING_APPROVAL → APPROVED → POSTED → REVERSED (+ REJECTED). |

### Ledger

| Table | Purpose |
|---|---|
| `ledger_accounts` | `PLATFORM_REWARD_EXPENSE` (no owner) and `MEMBER_REWARDS_PAYABLE` (per member), each per unit + currency. |
| `ledger_transactions` | REWARD_POSTING / REWARD_REVERSAL. Unique `idempotency_key` (`reward-posting:<id>`, `reward-reversal:<id>`); a reversal references the original (`reverses_transaction_id`, unique). |
| `ledger_entries` | DEBIT/CREDIT lines, `amount_minor > 0`. |
| `ledger_account_balances` (view) | Credits and debits per account. Member balance = credits − debits. |

### Audit, messaging, risk

| Table | Purpose |
|---|---|
| `audit_logs` | Append-only. Actor and roles, action, resource, before/after (redacted), reason, request id, IP. |
| `notifications` | In-app notifications per user. |
| `outbox_messages` | Transactional outbox ([ADR-0006](decisions/0006-transactional-outbox-bullmq.md)): topic, payload, `dedupe_key`, status, attempts, `available_at`, `locked_at`. |
| `member_flags` | Fraud signals and manual flags (OPEN / RESOLVED / DISMISSED). Advisory only. |

## Invariants

### Foreign-key actions (from the init migration)

- `RESTRICT` protects history. Users, programs, offerings, options and policy versions cannot
  be deleted while events, rewards, ledger rows, enrollments, closure rows, corrections or audit
  rows reference them.
- `CASCADE` is used only for owned, disposable children: sessions, email challenges, role grants,
  notifications and flags of a user; options, policy versions and admin assignments of a
  (DRAFT-only deletable) program; rules of a (DRAFT-only deletable) version.
- `SET NULL` applies to "who did it" columns (`created_by_id`, `approved_by_id`, …), so an actor
  reference never blocks anything. In practice users are deactivated, not deleted (see below).

## Referral tree (closure table)

Design and alternatives are in [ADR-0003](decisions/0003-referral-tree-closure-table.md).
`referral_relationships` is the adjacency list (who sponsored whom). `referral_paths` holds
every (ancestor, descendant, depth) pair, including depth-0 self rows. Both are written in the
same transaction as the user.

Example tree (depth from A):

```
A ─┬─ B ─┬─ D
   │     └─ E ── G
   └─ C ── F
```

`referral_paths` for G: `(G,G,0) (E,G,1) (B,G,2) (A,G,3)`.

### Write patterns

**Registration** (new user `$child` under `$sponsor`, in the registration transaction):

```sql
INSERT INTO referral_relationships (id, child_user_id, sponsor_user_id, referral_code_id, source)
VALUES (gen_random_uuid(), $child, $sponsor, $code_id, 'REGISTRATION');

INSERT INTO referral_paths (ancestor_id, descendant_id, depth)
SELECT ancestor_id, $child, depth + 1 FROM referral_paths WHERE descendant_id = $sponsor
UNION ALL
SELECT $child, $child, 0;
-- A member without a sponsor gets only the self row.
```

**Correction** (move `$m` and its subtree under `$s`; SUPER_ADMIN; one transaction):

```sql
SET LOCAL app.referral_correction = 'on';

-- Reject cycles: the new sponsor must not be $m or inside $m's subtree.
SELECT EXISTS (SELECT 1 FROM referral_paths WHERE ancestor_id = $m AND descendant_id = $s);  -- must be false

-- 1. Detach: remove paths from $m's strict ancestors to every node of $m's subtree.
DELETE FROM referral_paths p
USING referral_paths up, referral_paths sub
WHERE up.descendant_id = $m AND up.depth > 0          -- strict ancestors of $m
  AND sub.ancestor_id = $m                            -- $m's subtree (incl. $m)
  AND p.ancestor_id = up.ancestor_id
  AND p.descendant_id = sub.descendant_id;

-- 2. Attach: new upline ($s and its ancestors) × subtree.
INSERT INTO referral_paths (ancestor_id, descendant_id, depth)
SELECT up.ancestor_id, sub.descendant_id, up.depth + sub.depth + 1
FROM referral_paths up
JOIN referral_paths sub ON sub.ancestor_id = $m
WHERE up.descendant_id = $s;

-- 3. Adjacency + audit trail.
UPDATE referral_relationships
   SET sponsor_user_id = $s, source = 'ADMIN_CORRECTION', updated_at = now()
 WHERE child_user_id = $m;          -- INSERT instead if $m had no sponsor
INSERT INTO referral_corrections (...) VALUES (...);
-- + AuditService.record(tx, ...)
```

### Read patterns

All member-facing reads cap depth at 10 and select only privacy-safe columns (business rules
§6): display name = first name + last initial, depth, join date, status bucket, active-enrollment
flag, direct-referral count. Never email, phone, prices, rewards or sale amounts.

```sql
-- Direct children (depth 1), newest first, keyset-paginated.
SELECT r.child_user_id, r.attributed_at
FROM referral_relationships r
WHERE r.sponsor_user_id = $member
  AND (r.attributed_at, r.child_user_id) < ($cursor_at, $cursor_id)
ORDER BY r.attributed_at DESC, r.child_user_id DESC
LIMIT $limit;
-- (equivalently: referral_paths WHERE ancestor_id = $member AND depth = 1)

-- All descendants up to depth 10, ordered by level, keyset-paginated on (depth, descendant_id).
SELECT p.descendant_id, p.depth
FROM referral_paths p
WHERE p.ancestor_id = $member AND p.depth BETWEEN 1 AND 10
  AND (p.depth, p.descendant_id) > ($cursor_depth, $cursor_id)
ORDER BY p.depth, p.descendant_id
LIMIT $limit;

-- Ancestors (upline), nearest first — used by the reward engine (FORFEIT: up to max_depth;
-- COMPRESS: search up to depth 50).
SELECT p.ancestor_id, p.depth
FROM referral_paths p
WHERE p.descendant_id = $subject AND p.depth BETWEEN 1 AND $max_depth
ORDER BY p.depth;

-- The ancestor exactly N levels up (unique by (descendant_id, depth)).
SELECT ancestor_id FROM referral_paths WHERE descendant_id = $member AND depth = $n;

-- Team size per depth (+ how many are active / hold an active enrollment in a program).
SELECT p.depth,
       count(*)                                         AS members,
       count(*) FILTER (WHERE u.status = 'ACTIVE')      AS active,
       count(*) FILTER (WHERE EXISTS (
         SELECT 1 FROM program_enrollments e
         WHERE e.user_id = p.descendant_id AND e.program_id = $program AND e.status = 'ACTIVE'
       ))                                               AS enrolled
FROM referral_paths p
JOIN users u ON u.id = p.descendant_id
WHERE p.ancestor_id = $member AND p.depth BETWEEN 1 AND 10
GROUP BY p.depth
ORDER BY p.depth;

-- Whole-team size (all depths, e.g. for admins).
SELECT count(*) - 1 AS team_size FROM referral_paths WHERE ancestor_id = $member;

-- Search within a member's team by name (members never search by email).
SELECT p.descendant_id, p.depth, u.full_name, u.created_at
FROM referral_paths p
JOIN users u ON u.id = p.descendant_id
WHERE p.ancestor_id = $member AND p.depth BETWEEN 1 AND 10
  AND u.full_name ILIKE '%' || $term || '%'          -- escape % and _ in $term
ORDER BY p.depth, u.full_name
LIMIT 25;

-- Direct-referral count for a page of descendants.
SELECT r.sponsor_user_id, count(*) AS direct_referrals
FROM referral_relationships r
WHERE r.sponsor_user_id = ANY($descendant_ids)
GROUP BY r.sponsor_user_id;

-- Is $x inside $y's subtree? (cycle check, admin scoping)
SELECT EXISTS (SELECT 1 FROM referral_paths WHERE ancestor_id = $y AND descendant_id = $x);
```

### Consistency check

The closure must equal the transitive closure of the adjacency list. Use this in reconciliation
and tests. It returns zero rows when consistent:

```sql
WITH RECURSIVE chain AS (
  SELECT r.sponsor_user_id AS ancestor_id, r.child_user_id AS descendant_id, 1 AS depth
  FROM referral_relationships r
  UNION ALL
  SELECT r.sponsor_user_id, c.descendant_id, c.depth + 1
  FROM chain c
  JOIN referral_relationships r ON r.child_user_id = c.ancestor_id
  WHERE c.depth < 1000
)
(SELECT ancestor_id, descendant_id, depth FROM chain
 EXCEPT SELECT ancestor_id, descendant_id, depth FROM referral_paths WHERE depth > 0)
UNION ALL
(SELECT ancestor_id, descendant_id, depth FROM referral_paths WHERE depth > 0
 EXCEPT SELECT ancestor_id, descendant_id, depth FROM chain)
UNION ALL
(SELECT id, id, 0 FROM users
 EXCEPT SELECT ancestor_id, descendant_id, depth FROM referral_paths WHERE depth = 0);
```

## Concurrency strategy

The rules below are binding for every service that writes these tables.

1. **One use case = one transaction.** Multi-row writes use `prisma.$transaction`. Audit rows
   (`AuditService.record(tx, …)`) and outbox messages (`OutboxService.enqueue(tx, …)`) are
   written **inside** the same transaction. Nothing external (email, HTTP) happens inside a
   transaction.
2. **Unique constraints are the race arbiters.** Do not "check then insert". Insert, and map the
   unique violation (P2002 / 23505) to the domain error. This covers:
   - double enrollment (`uq_enrollments_one_open_per_program` → `ALREADY_ENROLLED`);
   - duplicate events (`(source, external_id)` → return the existing event);
   - double calculation (`reward_calculations.event_id`);
   - duplicate rewards (`(event_id, level)`, `(event_id, recipient)`);
   - double posting or reversal (`idempotency_key`, `reverses_transaction_id`);
   - ledger account get-or-create (partial uniques → re-select on conflict);
   - registration races on email (`users.email`);
   - outbox duplicates (`dedupe_key`).
3. **Row locks for state machines.** Event processing and reversal `SELECT … FOR UPDATE` the event
   row first and re-check its status (skip if already PROCESSED). Reward approve, reject or
   reverse locks the reward row (`FOR UPDATE`) and re-checks status. Status triggers reject
   illegal transitions regardless. Bulk approval processes each reward in its own transaction.
4. **Optimistic concurrency for edits.** Program and platform-settings updates include
   `WHERE id = $id AND version = $expected` and `version = version + 1`. Zero rows updated →
   `409 STALE_VERSION`. The client refetches and retries.
5. **Policy publication** relies on the exclusion constraint. Close the currently open version at
   `T` and publish the new one in the same transaction. A concurrent conflicting publish fails on
   `ex_policy_versions_no_overlap` (→ `409 INVARIANT_VIOLATION` / `CONFLICT`).
6. **Referral tree writes** share one transaction-level advisory lock key
   (`hashtext('referral-tree')`):
   - A **correction** takes it **exclusively**: `SELECT pg_advisory_xact_lock(hashtext('referral-tree'))`.
     It then runs the cycle check, sets `SET LOCAL app.referral_correction = 'on'`, and rewrites
     the closure rows and the relationship.
   - A **registration** takes it **shared** (`pg_advisory_xact_lock_shared(...)`) before reading
     the sponsor's upline and inserting the new closure rows.

   Registrations never block each other (they only append below an existing sponsor). Without
   the lock, a registration under a member who is being moved could copy the *old* upline after
   the correction computed its subtree, leaving stale paths. Readers always see either the old or
   the new tree (MVCC).
7. **Outbox relay** claims rows with `FOR UPDATE SKIP LOCKED` (safe with several workers) and
   reclaims `PROCESSING` rows whose lock is older than 5 min.
8. **Ledger** writes entries in the same transaction as the reward status change. The deferred
   balance trigger validates at COMMIT. Never split a posting across transactions.
9. **Isolation level:** READ COMMITTED (default) plus the locks and constraints above. Use
   SERIALIZABLE only for a use case that reads a set and writes based on it without a natural
   unique key, and retry on `40001`.
10. **Idempotent API mutations** (financial endpoints accepting `Idempotency-Key`) store the key
    and the response fingerprint, and replay the original result. A key reused with a different
    payload → `409 IDEMPOTENCY_CONFLICT`.

## Deletion and retention policies

| Data | Policy |
|---|---|
| Users | **Never hard-deleted** (closure self rows, events, rewards and audit reference them with RESTRICT). Members deactivate (`DEACTIVATED`, terminal); admins suspend/reactivate. Privacy erasure, if required, means anonymizing PII columns (name, email → placeholder, phone, avatar), never deleting rows. |
| Sessions | Revoked on logout, password change and suspension. Expired and revoked rows may be purged after 30 days by a scheduled job. |
| Email challenges | Consumed, invalidated and expired rows may be purged after 7 days (no raw codes are ever stored). |
| Roles / grants | Grants removed by SUPER_ADMIN (audited); the last SUPER_ADMIN cannot be removed. Role and permission catalogue rows are seed-managed. |
| Offerings | Deactivate (`INACTIVE`). Deleting is blocked once a program references them. |
| Programs | DRAFT: deletable (cascades options, draft policy versions, admin assignments). Otherwise: complete → archive, never delete (trigger). |
| Program options | Deactivate (`is_active = false`). Enrollments reference them (RESTRICT). Price or duration change = new option. |
| Enrollments | Never deleted. Terminal statuses (CANCELLED, EXPIRED, REJECTED) are final. |
| Referral relationships / paths | Never deleted except inside the audited correction workflow (trigger). Corrections are append-only. |
| Policy versions / rules | DRAFT: deletable (rules cascade). PUBLISHED/RETIRED: immutable, never deleted. |
| Qualifying events | Never deleted (trigger). Refunds and chargebacks = reversal. |
| Calculations / rewards | Never deleted (triggers). Rejected or reversed rewards stay as history. |
| Ledger accounts / transactions / entries | Append-only, never deleted (triggers). Corrections are compensating transactions. |
| Audit logs | Append-only, never deleted by the application. Archive to cold storage by partitioning or export per the retention policy agreed with legal (suggest ≥ 7 years for financial records). |
| Notifications | Deleted with their user (cascade). May be purged after 180 days once read. |
| Outbox messages | `SENT` purged after 14 days by the `outbox-cleanup` job. `DEAD` kept for investigation. One-time codes are redacted from email payloads once SENT/DEAD. |
| Member flags | Never deleted. Resolved or dismissed with a resolution note. |

## Working with migrations

- Never edit an applied migration (Prisma checksums them). Fix forward with a new migration.
- Create migrations without `migrate dev` (it is interactive and can reset data):

  ```bash
  cd apps/api
  corepack pnpm exec prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script \
    > prisma/migrations/$(date -u +%Y%m%d%H%M%S)_<name>/migration.sql
  corepack pnpm db:deploy
  ```

- Hand-written invariant SQL goes into its own migration (or the end of the generated one). Add
  a row to the [Invariants](#invariants) tables above and an integration test that proves the
  guard rejects the bad write.
- `CREATE INDEX CONCURRENTLY` cannot run inside a transaction block. Put it alone in a migration.
- Deployment, backups and rollback: [deployment.md](deployment.md#7-database-migrations).
